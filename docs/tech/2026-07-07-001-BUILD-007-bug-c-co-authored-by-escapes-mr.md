# BUG-C: Co-Authored-By de IA se escapa a MRs

**Módulo**: `.claude/hooks/sofka-asdd-guard-co-authored-by.mjs` (o el nombre real del hook — ver evidencia) + `.claude/skills/sofka-asdd-tech-lead-create-mr/SKILL.md` + `.claude/settings.json` (matchers)
**Severidad**: HIGH
**Prioridad**: P1
**Categoría preliminar**: bug
**Reportado**: 2026-07-07
**Estado**: Abierto
**Release asignado**: R2 (v2.27.2)
**Run ASDD**: 2026-07-07-001

> **Nota sobre ubicación**: este reporte vive en `docs/tech/` en lugar
> de `docs/specs/bug-*.md` por el defecto A8 (analyze-guard) documentado
> en BUG-A. Se re-ubica con `git mv` una vez A8 esté implementado.

## Descripción

El guard que impone la prohibición de "Co-Authored-By: Claude" y
similares atribuciones de IA (regla explícita en los skills
`sofka-asdd-tech-lead-create-mr` y `sofka-asdd-tech-lead-commit`) tiene
cobertura incompleta: solo se registra en el matcher `Bash` con una
allowlist de 3 comandos (`git commit`, `glab mr create`, `gh pr create`)
y busca únicamente el trailer literal `Co-Authored-By`. Múltiples
vectores de escape existen y **ya fueron materializados en campo**:
un MR real del consumidor terminó con "Co-Authored-By: Claude Opus 4.8"
en su descripción, visible en producción. El skill `create-mr` solo
prohíbe la atribución por texto (conducta), no por gate mecánico —
prosa sin enforcement, el patrón exacto del síntoma FLUJO.

## Pasos para reproducir

### Vector 1 — glab mr update / gh pr edit post-creación

1. El agente crea un MR limpio con `glab mr create --title "..." --description "..."` (pasa el guard).
2. Más tarde, el agente ejecuta
   `glab mr update {IID} --description "$(cat <<EOF ... Co-Authored-By: Claude ... EOF)"` para "corregir" o "enriquecer" la descripción.
3. El guard no reconoce `glab mr update` en su allowlist (`isTargetCommand()`) — pasa sin evaluar.
4. El MR ahora tiene la atribución de IA. Reproducido en campo por el
   consumidor.

### Vector 2 — Contenido pre-escrito con Write y pasado por -F/--description-file/--body-file

1. El agente escribe un archivo `.tmp/mr-body.md` con el trailer
   `Co-Authored-By: Claude`.
2. Ejecuta `glab mr create ... --description-file .tmp/mr-body.md` o
   `gh pr create ... --body-file .tmp/mr-body.md`.
3. El comando Bash **solo contiene la ruta del archivo**, no el
   contenido — el guard busca el trailer en el string del comando, no
   lo encuentra, pasa el gate.
4. El MR queda con la atribución.

### Vector 3 — glab api / gh api directos

1. El agente construye un payload JSON con la descripción del MR
   incluyendo `Co-Authored-By`.
2. Ejecuta
   `glab api projects/:id/merge_requests --method POST --field description=@body.json`
   o `gh api /repos/:o/:r/pulls --field body=@body.json`.
3. El comando no coincide con ninguno de los 3 comandos allowlisted; el
   guard pasa. El MR queda con la atribución.

### Vector 4 — Patrón sin el trailer literal

1. El agente incluye en la descripción del MR el string
   `"🤖 Generated with Claude Code"` o `"Assisted by Claude"` sin usar
   `Co-Authored-By`.
2. La regex del guard `/Co-Authored-By:.*(Claude|Anthropic)/i` no
   matchea el emoji ni las variantes en prosa.
3. El MR queda con la atribución en formato distinto.

Los 4 vectores han sido observados o son fácilmente reproducibles. El
vector 1 ya se materializó en un MR del consumidor.

## Comportamiento esperado

El guard debe bloquear **cualquier** atribución de IA en cualquier vía
de creación o modificación de MRs/PRs/commits, incluyendo:

- Todos los comandos que crean o modifican MRs/PRs: `glab mr create/update/edit`, `gh pr create/edit`, `glab api merge_requests`, `gh api pulls`.
- Payloads pasados por `--description-file`, `--body-file`, `-F`, `--field description=@archivo` — validar el contenido del archivo.
- Variantes textuales: `Co-Authored-By: (Claude|Anthropic|Sonnet|Opus|Haiku)`, `🤖 Generated with Claude`, `Generated by Claude`, `Assisted by (Claude|Anthropic)`, "Written by Claude", etc.

## Comportamiento actual

- **`isTargetCommand()`** (línea `:65-73` del guard): allowlist de 3
  comandos — `git commit`, `glab mr create`, `gh pr create`. Cualquier
  otro comando (`update`, `edit`, `api`) pasa sin evaluar.
- **Regex de detección** (`:82-85`):
  aproximadamente `/Co-Authored-By:.*(Claude|Anthropic)/i` o similar,
  ceñida al trailer canónico. No cubre el emoji "🤖 Generated with" ni
  variantes en prosa.
- **Sin lectura de archivos**: el guard analiza el string del comando
  Bash. Si el contenido viene por `-F`/`--description-file`/`--body-file`,
  el comando solo lleva el nombre del archivo — el contenido nunca se
  inspecciona.
- **Sin registro en matcher `Write`**: el archivo pre-generado con
  atribución (típico paso 2 de vector 2) se escribe sin ser interceptado.
  El propio guard debería complementarse con una verificación en
  `Write` filtrando paths donde no debe aparecer (excepto `test/`,
  `spec/`, `__tests__/` que legítimamente contienen el string como
  fixture).
- **El skill `create-mr` solo prohíbe por texto (conducta)** — la
  sección "Regla de atribución" documenta el "no" pero no hay
  enforcement mecánico complementario al del guard. Materializado en
  campo: el MR con "Co-Authored-By: Claude Opus 4.8" visible en el
  consumidor.

## Ambiente

- **Versión / commit**: lock v2.27.0

## Evidencia

- **Materialización en campo**: MR real del consumidor con
  "Co-Authored-By: Claude Opus 4.8" en la descripción, visible tras el
  merge. El equipo tuvo que editar manualmente para removerlo.
- **`isTargetCommand()` (:65-73)**: allowlist limitada a 3 comandos.
- **Regex (:82-85)**: matchea el trailer canónico, no variantes.
- **Skill `create-mr`**: prohíbe por prosa (sección "Regla de
  atribución (no negociable)"), sin gate complementario al del guard.
- **Skill `commit`**: mismo patrón — prohibición en prosa, sin gate
  complementario.

## Análisis preliminar (SBR-001)

**Causa raíz**: el guard cubre un happy-path angosto (comandos canónicos
+ trailer canónico) y confía en la conducta del agente para todo lo
demás. Cualquier variante mínima escapa el gate. En un sistema donde el
agente escribe la descripción del MR, la asunción de conducta es
peligrosa — vector 1 (update posterior) es literalmente el patrón que
el agente usaría para "mejorar" un MR ya creado, sin ninguna intención
maliciosa.

**Áreas de regresión en riesgo tras el fix**:

- Fixtures de test que contienen legítimamente el string
  `"Co-Authored-By"` como parte de su verificación deben ser excluidos
  del matcher `Write` (paths `test/`, `spec/`, `__tests__/`,
  `**/*.test.md`, etc.).
- Comandos legítimos del equipo que usan `glab api` o `gh api` para
  operaciones no relacionadas con MRs no deben ser bloqueados por
  ampliar la allowlist demasiado agresivamente.
- Skills de otros agentes (developer-frontend/backend) que escriben
  código de tests con el string como fixture deben poder hacerlo bajo
  paths excluidos.

## Fix sugerido (propuesta — validar en diagnóstico, ver R2 en el plan)

**Cambio propuesto**:

- **C1** — Ampliar la allowlist de `isTargetCommand()`:
  ```
  git commit
  glab mr create | glab mr update | glab mr edit
  gh pr create | gh pr edit
  glab api merge_requests (con --method POST|PUT|PATCH)
  gh api pulls | gh api /repos/.../pulls (con --method POST|PATCH)
  ```
  Detección basada en el argumento del comando, no en el binario solo.
- **C2** — Detectar el patrón
  `/🤖\s*Generated with (Claude|Anthropic)|by (Claude|Anthropic)|Assisted by (Claude|Anthropic)|Written by (Claude|Anthropic)/i`
  **independiente** del trailer `Co-Authored-By`. Ambas verificaciones
  se aplican en paralelo (OR).
- **C3** — Registrar el guard también en el matcher `Write`, con filtro
  de paths que excluya `test/`, `spec/`, `__tests__/`, `.tmp/`,
  `docs/tech/bug-*.md` (fixtures y este mismo reporte). Cuando un
  archivo va a ser escrito con el string bajo un path NO excluido →
  bloquear. Cubre vector 2 (pre-escritura del cuerpo del MR).

  **C3 refinado (R2b):** el matcher `Write` usa allowlist positiva de
  paths candidatos (`mr-body`/`pr-body`/`description`/`.tmp/…`) en vez
  de escanear todo `.md` — la exclusión literal `docs/tech/bug-*.md`
  del contrato original era insuficiente: no cubría el plan maestro
  (`BUILD-001`, sin "bug" en el nombre) ni el `SKILL.md` de
  `sofka-asdd-tech-lead-create-mr`, y ambos quedaban bloqueados al
  editarlos porque legítimamente contienen el string
  "Co-Authored-By" como documentación. La contradicción del spec sobre
  `.tmp/` se resuelve a favor del Vector 2: `.tmp/` SÍ es candidato
  (para poder seguir bloqueando cuerpos de MR/PR staged ahí antes de
  `--description-file`/`--body-file`), y la allowlist positiva por
  basename evita que documentación del template (`docs/tech/`,
  `SKILL.md`, `CLAUDE.md`, planes maestros) sea escaneada.
- **C4** — Actualizar el skill `sofka-asdd-tech-lead-create-mr` para
  reforzar la prohibición con ejemplos de los 4 vectores identificados
  (docs). El skill sigue siendo la fuente de conducta esperada; el
  guard es el enforcement mecánico complementario.
- **C5** — Tests extendidos cubriendo cada vector:
  - `glab mr update` con trailer → bloqueado.
  - `--description-file body.md` con body.md conteniendo el trailer →
    bloqueado por matcher `Write` sobre `body.md`.
  - `glab api projects/:id/merge_requests --field description=@...` →
    bloqueado por comando + validación del payload si es inline.
  - `🤖 Generated with Claude Code` sin trailer → bloqueado por C2.
  - Fixture legítima bajo `test/` con el string → NO bloqueada.

**Archivos candidatos**:

- `.claude/hooks/sofka-asdd-guard-co-authored-by.mjs` (nombre exacto a
  verificar; puede diferir).
- `.claude/settings.json` (registrar el hook también en matcher
  `Write`).
- `.claude/skills/sofka-asdd-tech-lead-create-mr/SKILL.md`.
- `.claude/skills/sofka-asdd-tech-lead-commit/SKILL.md`.
- Tests del hook (crear o extender).

**Tests requeridos**: enumerados en C5 arriba. Cada vector = 1 test
positivo (bloqueo esperado) + 1 test negativo (comando análogo sin
atribución = pasa).

**Riesgo del fix**: **bajo-medio**. Amplía cobertura pero no cambia la
semántica del gate; el fail-closed sigue siendo el comportamiento por
default. El único riesgo real es falsos positivos sobre fixtures de
test — se mitiga con la lista de paths excluidos en C3.
