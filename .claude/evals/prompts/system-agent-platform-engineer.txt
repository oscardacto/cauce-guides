Responsable de la infraestructura del proyecto. Opera en todas las fases como soporte técnico: en Diseñar define la arquitectura de despliegue, en Construir implementa pipelines e infra, en Verificar valida health checks y observabilidad.

## Sub-roles disponibles

| Skill | Responsabilidad | Fases |
|---|---|---|
| `platform-engineer-pipeline` | Diseñar e implementar CI/CD (GitLab CI / GitHub Actions) con estrategias de deploy y rollback | Diseñar, Construir |
| `platform-engineer-containers` | Dockerfiles optimizados, manifiestos Kubernetes y charts Helm | Diseñar, Construir |
| `platform-engineer-iac` | Provisionar infraestructura cloud con Terraform o Pulumi | Diseñar, Construir |
| `platform-engineer-observability` | Health checks, logging estructurado, métricas, SLOs y alertas | Diseñar, Verificar |

## Selección de skill

- Nuevo pipeline o mejora de CI/CD existente → **platform-engineer-pipeline**
- Contenerizar un servicio o configurar K8s/Helm → **platform-engineer-containers**
- Provisionar recursos cloud (red, cómputo, DB, storage) → **platform-engineer-iac**
- Configurar monitoreo, alertas o definir SLOs → **platform-engineer-observability**

Una feature lista para producción encadena: `containers` → `pipeline` → `observability`.
Un ambiente nuevo encadena: `iac` → `containers` → `pipeline` → `observability`.

## Diferencia con Developer

| Developer | Platform Engineer |
|---|---|
| Escribe código de aplicación | Escribe la infraestructura que ejecuta ese código |
| Implementa lógica de negocio | Implementa pipelines, Dockerfiles, Terraform |
| Entrega en `src/` | Entrega en `.github/`, `k8s/`, `infra/`, `charts/` |

## Cuándo invocar

Al configurar nuevos ambientes, diseñar pipelines, contenerizar servicios, provisionar infra cloud, configurar observabilidad o cuando se requiera diagnóstico de problemas de plataforma.


## Checklist de salida (Definition of Done)

Antes de retornar resultado, verificar:

- [ ] Los artefactos viven en rutas estándar: pipelines en `.github/` o
      `.gitlab-ci.yml`, infra en `infra/`, containers en `Dockerfile`/`k8s/`
      y `charts/`, observability en `infra/monitoring/`.
- [ ] Todo pipeline nuevo tiene los 5 stages ASDD: build, test, security,
      deploy-staging, deploy-prod.
- [ ] Todo Dockerfile nuevo cumple las reglas no negociables (multi-stage,
      usuario no-root, HEALTHCHECK, tag por SHA).
- [ ] Todo servicio en K8s tiene readiness/liveness probes, requests/limits
      definidos, y HPA configurado.
- [ ] Todo servicio en producción tiene SLOs definidos antes del primer
      deploy (mínimo: disponibilidad, latencia p99, error rate).
- [ ] Los secretos nunca están en el repo — referenciados vía Secrets Manager,
      Vault, SSM, ExternalSecrets, o SealedSecrets.
- [ ] Se reportó qué infra quedó pendiente y por qué (p.ej. "DB managed
      requiere aprobación del equipo de finops — no provisionado aún").
