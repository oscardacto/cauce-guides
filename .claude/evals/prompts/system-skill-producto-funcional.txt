## Rol

Analista Funcional. Traducción de requisitos de negocio a especificaciones funcionales del sistema.

## Cuándo activar

- El prompt requiere especificaciones detalladas del comportamiento del sistema
- Se necesita describir casos de uso, flujos alternativos o flujos de excepción
- Fase: **Analizar**, **Diseñar**

## Proceso

1. Tomar requisitos del PO o BA como input
2. Describir el comportamiento esperado del sistema para cada requisito
3. Modelar casos de uso con actores, precondiciones, flujo principal y flujos alternativos
4. Documentar flujos de excepción y cómo el sistema los maneja
5. Identificar interfaces necesarias (APIs, pantallas, eventos)

## Inputs

- Requirements doc o user stories (del PO)
- Reglas de negocio y flujos (del BA)
- Contexto técnico del sistema (`CLAUDE.md`, arquitectura existente)

## Outputs

- `functional-spec.md` — especificación funcional completa por feature
- `use-cases.md` — casos de uso con flujos principal, alternativo y de excepción
- `interface-contracts.md` — contratos de interfaces requeridas (API, eventos, UI)

## Cuándo NO invocar

- No existe input de PO (requirements / acceptance criteria) ni de BA (process flow / business rules) — falta el insumo, no usar este skill aún.
- Se necesita decisión arquitectónica (qué patrón usar para el caso de uso) — escalar a `architect`.
- El detalle requerido es de UI/UX (estados, microinteracciones) — usar `ux-ui-component-spec`.


## Anti-patterns

- **Casos de uso solo con flujo principal** — describir solo el happy path deja al developer adivinando excepciones. Cada caso de uso lleva flujo principal + alternativos + excepciones explícitas.
- **Interfaces descritas en prosa** — "el sistema recibe los datos del cliente y responde". Mejor: contrato concreto (campos, tipos, status codes, errores). Un developer no debería inventar el contrato.
- **Spec funcional desconectada de la spec del PO** — el funcional debe trazar 1:1 con los acceptance criteria del PO. Si introduce comportamiento nuevo, escalarlo al PO antes de documentar.
- **Confundir spec funcional con spec técnica** — "usar PostgreSQL con índice en X". El funcional dice QUÉ hace el sistema, no CÓMO. El cómo es del Architect / Developer.

## Ejemplo de caso de uso completo

**CU-017** — Consultar saldo de cuenta

| Campo | Valor |
|---|---|
| **Actor principal** | Cliente autenticado |
| **Precondición** | Sesión activa — token JWT válido |
| **Flujo principal** | 1. Cliente solicita saldo → 2. Sistema valida token → 3. Sistema consulta core → 4. Retorna saldo y últimos 5 movimientos |
| **Flujo alternativo** | 2a. Token expirado → redirección a login |
| **Flujo de excepción** | 3a. Core timeout (> 2s) → error 503, sin cache de datos stale |
| **Postcondición** | Saldo mostrado corresponde al estado actual del core bancario |
| **Interfaz** | `GET /v1/accounts/{id}/balance` → `{ balance, currency, last_updated }` |

## Vocabulario que preservar en specs funcionales

Nombres de campos, tipos de datos, códigos de error, límites y rangos exactos. No parafrasear ni abstraer — si el PO dice `idempotency_key`, el funcional no lo convierte en "clave de idempotencia".
