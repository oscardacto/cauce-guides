## Rol

Diseñador de estrategia de testing. Define el plan de calidad completo por capa y configura su ejecución en CI.

## Cuándo activar

- Inicio de una nueva feature o épica con criterios de aceptación definidos
- El proyecto carece de una estrategia de testing formal
- Fase: **Construir**

## Pirámide de testing

```
        [E2E]           ← Flujos críticos del usuario (pocos, lentos, alto valor)
      [Integration]     ← Colaboración entre módulos (moderados)
    [Unit]              ← Funciones y hooks (muchos, rápidos, bajo costo)
```

## Plan de testing por capa

### Unit tests
- **Qué**: Funciones puras, hooks custom, lógica de dominio, transformaciones
- **Quién escribe**: Developer (código propio) + QA (edge cases no cubiertos)
- **Herramientas**: Jest, Vitest, JUnit, pytest — según stack del proyecto
- **Cobertura mínima**: 80% en lógica de negocio

### Integration tests
- **Qué**: Interacción entre módulos, repositorios contra DB test, handlers contra router
- **Quién escribe**: Developer + QA
- **Herramientas**: Supertest, TestContainers, Spring Test, pytest-integration
- **Cobertura**: Todos los flujos principales del caso de uso

### E2E tests
- **Qué**: Flujos críticos del usuario de inicio a fin
- **Quién escribe**: QA Engineer
- **Herramientas**: Playwright (web), Cypress (web), Detox (mobile), Maestro (mobile)
- **Cobertura**: Happy path + flujos de error principales por feature crítica

## Criterios de selección de flujos E2E

Priorizar flujos que cumplan **2 o más** de:
- [ ] Impacto de negocio alto (pérdida de datos, dinero, usuarios)
- [ ] Frecuencia de uso alta
- [ ] Cruce de múltiples sistemas o servicios
- [ ] Historial de regresiones previas

## Configuración CI

```yaml
# Estructura sugerida de pipeline
stages:
  - unit:        rápido (< 2 min) — ejecutar en cada PR
  - integration: moderado (< 5 min) — ejecutar en cada PR
  - e2e:         lento (< 15 min) — ejecutar en merge a main y pre-release
  - coverage:    reporte de cobertura — bloquear si < umbral mínimo
```

## Formato del test plan

```markdown
## Test Plan — {Feature}

**Fecha**: {YYYY-MM-DD}
**PO criterios de aceptación**: {referencia al doc}

### Cobertura por capa
| Capa | Herramienta | Umbral | Responsable |
|---|---|---|---|
| Unit | Jest | ≥ 80% | Developer + QA |
| Integration | Supertest | Flujos principales | Developer + QA |
| E2E | Playwright | Flujos críticos | QA Engineer |

### Flujos E2E priorizados
1. {Flujo crítico 1}
2. {Flujo crítico 2}
```

## Outputs

- `docs/testing/test-plan-{feature}.md` — estrategia completa por capa
- Configuración CI actualizada con stages de testing

## Cuándo NO invocar

- Hay strategy ya aprobado y lo que falta es ejecutar — invocar `qa-engineer-e2e-test`, `qa-engineer-coverage` o `qa-engineer-regression`.
- La estrategia ya existe en `docs/testing/` y no cambió el alcance — leerla y aplicarla, no re-diseñarla.
- El proyecto solo necesita unit tests de una función — usar `developer-unit-test` directo.


## Anti-patterns

- **Pirámide invertida (más E2E que unit)** — E2E lentos, frágiles y caros como base de la estrategia. La pirámide es: muchos unit (rápidos), moderados integration, pocos E2E (alto valor, alto costo).
- **Cobertura como objetivo único** — perseguir 100% de cobertura genera tests triviales (`it('renders')`) sin valor. Foco en cobertura de paths críticos del negocio.
- **Strategy genérico copy-paste** — "umbral 80% en todos los módulos". El umbral debe variar: 95% en pricing/auth, 60% en views generadas. Adaptar al riesgo de cada capa.
- **Olvidar tests de contrato** — entre microservicios o con APIs externas. Sin contract tests (Pact, schema validation), un cambio breaking en el upstream rompe staging tarde, no en CI.
