## Rol

Validador de cumplimiento. Evalúa el sistema contra requerimientos formales de PCI-DSS y OWASP ASVS y produce evidencia de cumplimiento o lista de gaps.

## Cuándo activar

- Previo a auditorías externas de seguridad o certificaciones
- Al completar una feature con manejo de datos de pago o datos sensibles regulados
- Revisión periódica de cumplimiento (recomendado: por release mayor)
- Fase: **Verificar**

## Cuándo NO invocar

- El alcance es hallazgos de código (no checklist formal) — usar `security-code-scan`.
- Se buscan secrets hardcoded — usar `security-secrets-scan`.
- Solo se necesita validar dependencias — usar `security-dependency-audit`.


## OWASP ASVS — Application Security Verification Standard

Niveles de verificación:

| Nivel | Descripción | Cuándo aplicar |
|---|---|---|
| L1 | Opportunistic — controles mínimos | Aplicaciones internas de bajo riesgo |
| L2 | Standard — controles estándar | Mayoría de aplicaciones con datos de usuarios |
| L3 | Advanced — controles exhaustivos | Aplicaciones críticas, datos médicos o financieros |

### Checklist ASVS L2 (selección de controles críticos)

#### Autenticación (V2)
- [ ] Passwords almacenados con hash adaptativo (bcrypt, Argon2, PBKDF2)
- [ ] MFA disponible para cuentas privilegiadas
- [ ] Rate limiting en endpoints de autenticación
- [ ] Tokens de sesión con expiración y rotación tras login

#### Control de Acceso (V4)
- [ ] Principio de mínimo privilegio aplicado
- [ ] Verificación de autorización en el servidor, no solo en el cliente
- [ ] Acceso a recursos validado por ownership del usuario

#### Validación de Inputs (V5)
- [ ] Todos los inputs de usuario validados en el servidor
- [ ] Salida codificada según el contexto (HTML, SQL, JS, URL)
- [ ] Protección contra mass assignment

#### Criptografía (V6)
- [ ] TLS 1.2+ en todas las comunicaciones externas
- [ ] Datos sensibles cifrados en reposo
- [ ] Sin algoritmos débiles (MD5, SHA1, DES, RC4)

#### Manejo de Errores y Logging (V7)
- [ ] Sin stack traces o detalles internos expuestos al usuario
- [ ] Eventos de seguridad loggeados (login, logout, fallos de auth, cambios de permisos)
- [ ] Logs sin datos sensibles (passwords, tokens, PII)

## PCI-DSS — Selección de requerimientos aplicables a software

| Req. | Descripción | Evidencia requerida |
|---|---|---|
| 3.x | Protección de datos de tarjeta almacenados | Cifrado de PAN, no almacenar CVV |
| 4.x | Cifrado en transmisión | TLS en todas las rutas con datos de pago |
| 6.x | Desarrollo seguro | SAST ejecutado, vulnerabilidades OWASP remediadas |
| 7.x | Control de acceso | Acceso a datos de pago por necesidad de negocio |
| 10.x | Logging y monitoreo | Logs de acceso a datos de pago retenidos ≥ 12 meses |

## Formato de reporte

```markdown
## Compliance Report — {sistema / feature}

**Fecha**: {YYYY-MM-DD}
**Estándares evaluados**: OWASP ASVS L2 / PCI-DSS v4.0
**Resultado**: ✅ Cumple | ⚠️ Cumple con observaciones | ❌ No cumple

### Gaps identificados

| ID | Estándar | Control | Estado | Remediación requerida | Prioridad |
|---|---|---|---|---|---|
| C-001 | ASVS V2 | Hash de passwords | ❌ | Migrar de MD5 a Argon2 | Critical |
```

## Outputs

- `docs/security/compliance-{fecha}.md` — checklist completo con evidencia y gaps priorizados

## Gotchas

- **Cumplimiento documental sin evidencia técnica** — checklist con todos los ítems en ✅ pero sin captura, log o test que lo respalde. Auditor externo lo rechaza. Cada PASS lleva referencia a artefacto verificable (test ID, log path, configuración).
- **PCI-DSS sin reducir el alcance del CDE** — almacenar PAN cifrado en toda la BD obliga a auditar todo el sistema. Tokenización + segmentación de red reduce alcance dramáticamente. Diseñar para alcance mínimo desde el inicio.
- **ASVS L3 cuando solo se necesita L2** — sobre-controlar genera fricción operativa sin valor. Validar el nivel correcto: L1 internas, L2 con datos de usuario, L3 solo crítico (financiero, salud).
- **Compliance puntual vs continuo** — "pasamos la auditoría" en marzo, en abril llega un PR que rompe controles. Compliance se valida en cada release, no anualmente. Automatizar checks (SAST, secrets, dep audit) en CI.
- **HIPAA/GDPR aplicado solo a producción** — entornos de dev/staging con datos reales también caen bajo el estándar. Datos sintéticos o anonimizados en todo entorno no productivo.
