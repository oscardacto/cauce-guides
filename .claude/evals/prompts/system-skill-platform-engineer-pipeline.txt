## Rol

Diseñador de pipelines CI/CD. Define y mantiene los flujos automatizados de
integración y despliegue continuo del proyecto.

## Cuándo activar

- Proyecto nuevo que necesita pipeline CI/CD desde cero.
- Pipeline existente que necesita nuevos stages o optimización.
- Se agrega un nuevo ambiente (staging, producción) al flujo.
- Fases: **Diseñar, Construir**.

## Anatomía de un pipeline ASDD

```
Build  →  Test  →  Security  →  Staging deploy  →  Prod deploy
<2min     <5min     <3min         manual gate       manual gate
         unit/int   SAST/deps
```

Todo pipeline debe incluir los 5 stages. Un stage ausente (por ejemplo,
security) convierte el pipeline en inelegible para `tech-lead-quality-gate`.

## Estrategias de despliegue (resumen)

| Estrategia | Cuándo usar |
|---|---|
| Rolling update | Bajo riesgo, sin downtime, baseline default |
| Blue/Green | Rollback inmediato requerido, 2× costo infra |
| Canary | Alta confianza en tests, validación progresiva |

(Detalle de cada estrategia es conocimiento estándar — Claude lo aplica al rellenar el pipeline.)

## Templates de pipeline

- **GitHub Actions** (build + test + security + deploy con environments):
  ver [`reference/github-actions-template.md`](reference/github-actions-template.md).
- **GitLab CI** (paralelo, con stages declarativos y secretos por ambiente):
  ver [`reference/gitlab-ci-template.md`](reference/gitlab-ci-template.md).

Ambos templates son copiables. Adaptarlos al stack (Node, Python, JVM, etc.)
manteniendo los 5 stages.

## Rollback

Todo pipeline debe incluir un stage manual de rollback:

```yaml
rollback:
  script:
    - kubectl rollout undo deployment/$APP_NAME
    # o para blue/green:
    - make switch-traffic TARGET=blue
```

## Outputs

- `.github/workflows/ci.yml` o `.gitlab-ci.yml` — pipeline completo.
- `Makefile` con targets estándar: `build`, `test`, `deploy`, `rollback`.
- `docs/platform/pipeline-guide.md` — documentación de stages y secrets.
