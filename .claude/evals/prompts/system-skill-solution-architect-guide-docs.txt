# Documentación de Arquitectura Guide — DA_ADE34 a DA_ADE48

Genera la documentación formal de arquitectura siguiendo el estándar corporativo Guide.
Cada documento usa un template en `reference/` como base.

## Cadena de dependencias entre documentos

```
DA_ADE36 Business Drivers      → ¿Por qué? Contexto y objetivos del cliente
DA_ADE35 Architecture Drivers  → ¿Qué? QAs, restricciones, riesgos, concerns
DA_ADE45 Architecture AS-IS    → Estado actual: C1, C2, capability map, gaps
DA_ADE44 Architecture TO-BE    → Estado futuro: C1, C2, C3, roadmap
DA_ADE34 ADR                   → Decisiones que justifican TO-BE (o AS-IS)
DA_ADE43 Arch Dependencies     → Dependencias entre componentes
DA_ADE42 RAD-Ar                → Adherencia y desviaciones al estándar
DA_ADE48 Minutograma           → Planeación de salida a ambientes
```

Generar siempre en orden de dependencias. Cada documento referencia los anteriores
para garantizar trazabilidad (ej. cada QA en DA_ADE35 se vincula a un OE de DA_ADE36).

## Árbol de decisión — qué documentos generar

| Contexto del usuario | Documentos a generar |
|---|---|
| Proyecto existente, documentar estado actual (AS-IS) | DA_ADE36 + DA_ADE35 + DA_ADE45 + DA_ADE34 + DA_ADE43 |
| Propuesta de diseño / modernización (TO-BE) | DA_ADE36 + DA_ADE35 + DA_ADE44 + DA_ADE34 + DA_ADE43 |
| Documentación completa (AS-IS + TO-BE) | Los 8 documentos |
| Salida a ambiente / release | DA_ADE48 + DA_ADE42 |

## Convenciones

- **Output:** `docs/architecture/DA_ADE{NN}_{slug-solucion}.md`
- **Slug:** kebab-case del nombre de la solución (ej. `core-bancario-pymes`)
- **Diagramas C1 / C2 / C3:** Mermaid con sintaxis C4 (`C4Context`, `C4Container`, `C4Component`)
- **ADRs múltiples:** `DA_ADE34_{slug}_ADR-{NNN}_{titulo}.md` cuando hay más de un ADR
- **Templates base:** carpeta `reference/` de este skill — copiar y reemplazar `{PLACEHOLDERS}`

## Información a solicitar al usuario si falta

Antes de generar, verificar que el contexto cubre estos elementos. Si alguno falta,
preguntar al usuario explícitamente antes de continuar (no inventar):

**Para DA_ADE36 (Business Drivers):**
- Nombre del cliente y línea de negocio
- País / región / mercados relevantes
- Regulaciones críticas aplicables (PCI-DSS, HIPAA, GDPR, SOX, etc.)
- Objetivos estratégicos con métricas y plazos
- Pain points actuales

**Para DA_ADE35 (Architecture Drivers):**
- QAs prioritarios (disponibilidad, rendimiento, seguridad, escalabilidad) con métricas
- Restricciones técnicas (sistemas legados intocables, presupuesto, stack obligatorio)
- Riesgos técnicos identificados

**Para DA_ADE45 (AS-IS):**
- Sistema bajo consideración (SBC) y su frontera
- Tecnologías actuales por contenedor
- Integraciones externas activas
- Gaps y limitaciones conocidas

**Para DA_ADE44 (TO-BE):**
- Patrón de arquitectura objetivo (microservicios, modular monolith, event-driven)
- Tecnologías target
- Roadmap por fases con hitos

**Para DA_ADE48 (Minutograma):**
- Ambiente destino (dev / qa / pdn)
- Ventana de despliegue
- Responsable de release y de rollback
- Prerrequisitos (migraciones, backups, etc.)

## Proceso recomendado

1. Determinar tipo de documentación (AS-IS, TO-BE, completo, release).
2. Verificar qué información ya existe en `docs/specs/`, `docs/architecture/decisions/`, `MEMORY.md`.
3. Solicitar al usuario lo faltante.
4. Para cada documento de la lista:
   - Leer el template de `reference/`
   - Reemplazar todos los `{PLACEHOLDER}` con información real
   - Validar que las referencias cruzadas (QA-XX, OE-XX, GAP-XX, ADR-XXX) sean consistentes
   - Escribir en `docs/architecture/DA_ADE{NN}_{slug}.md`
5. Al final, listar todos los archivos generados y resumir trazabilidad.

## ADR — convenciones de ciclo de vida

- **Naming:** `docs/architecture/decisions/ADR-{NNN}-{titulo-kebab}.md`
- **Estados válidos:** `Propuesta → Aceptada → Sustituida | Desaprobada` o `Propuesta → Rechazada`
- **Transiciones:**
  - `Propuesta → Aceptada`: registrar fecha y deciders. El cuerpo es inmutable tras aceptación.
  - `Aceptada → Sustituida`: el ADR sustituto DEBE existir en estado Aceptada primero. Agregar link bidireccional. NUNCA borrar el archivo viejo.
  - `Aceptada → Desaprobada`: solo si no hay reemplazo formal. Documentar por qué en el Status.
- **Commit de cambio de estado:** `chore(adr): ADR-XXX propuesta→aceptada`
- **Spec completa DA_ADE34:** `reference/guide-da_ade34-spec.md`
- **Template rellenable:** `reference/guide-da_ade34-template.md`
- **Ejemplo canónico:** `reference/adr-guide-cache-aside-redis.md`

## Reglas de calidad

- No inventar información: si falta, preguntar.
- Cada QA debe referenciar al menos un OE (objetivo estratégico) o RN (reto de negocio).
- Cada ADR debe evaluar al menos 2 alternativas con trade-offs concretos.
- Los diagramas Mermaid deben ser sintácticamente válidos y renderizables.
- Mantener trazabilidad: GAP-XX (AS-IS) → solución TO-BE → ADR-XXX que la justifica.
