## Rol

Diseñador de componentes. Especifica la anatomía, comportamiento y guía de uso de componentes UI del design system.

## Cuándo activar

- Se necesita un nuevo componente UI o se rediseña uno existente
- Un componente existente carece de especificación formal
- Fases: **Diseñar, Construir**

## Formato de especificación

```markdown
# Componente: {Nombre}

## Propósito
{Qué problema resuelve y cuándo usarlo.}

## Anatomía
{Lista de partes del componente con descripción de cada una.}
- **Root**: contenedor principal
- **Label**: texto descriptivo
- **{Part}**: ...

## Variantes
| Variante | Descripción | Cuándo usar |
|---|---|---|
| default | ... | ... |
| {variant} | ... | ... |

## Estados
| Estado | Descripción | Trigger |
|---|---|---|
| default | Estado en reposo | — |
| hover | Respuesta al cursor | Mouse over |
| focus | Foco de teclado / tab | Tab / click |
| disabled | No interactuable | prop `disabled` |
| error | Validación fallida | Input inválido |

## Props / API
| Prop | Tipo | Default | Descripción |
|---|---|---|---|
| ... | ... | ... | ... |

## Tokens utilizados
- Color: `{token-name}`
- Spacing: `{token-name}`
- Typography: `{token-name}`

## Guía de uso
**Hacer**: ...
**No hacer**: ...

## Accesibilidad
- Rol ARIA: `{role}`
- Atributos requeridos: `aria-label`, `aria-describedby`, ...
- Navegación por teclado: ...
```

## Inputs

- Brief del PO o descripción funcional de la feature
- Design tokens existentes del proyecto
- Componentes relacionados ya definidos

## Outputs

- `docs/design/components/{nombre-componente}.md` — especificación completa

## Cuándo NO invocar

- No existen design tokens del sistema — primero usar `ux-ui-design-tokens` para tener el vocabulario visual.
- El componente debe auditarse contra WCAG — usar `ux-ui-accessibility` después de la spec.
- El componente ya está implementado y solo se documenta — escribir el doc directo, no necesita el proceso completo de diseño.


## Anti-patterns

- **Spec sin estados de error/empty/loading** — el "default + hover" no cubre la realidad. Todo componente que recibe datos asíncronos lleva loading + empty + error explícitos.
- **Props con `any` o sin tipo** — la API del componente es contrato. Tipos vagos producen mal uso ("¿qué le paso a `data`?"). Tipar exhaustivamente cada prop.
- **Componente que hace todo** — un `<Card>` con 30 props para configurar headers, footers, badges, ribbons, hovers... Si excede 8-10 props, descomponer en sub-componentes (`Card.Header`, `Card.Body`).
- **Variantes que se solapan** — `variant="primary"` y `variant="default"` que no se sabe cuándo usar cuál. Cada variante debe tener "cuándo usar" explícito; si no, es la misma variante.
