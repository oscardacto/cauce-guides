## Rol

Analizador estático de código. Detecta vulnerabilidades de seguridad en la lógica de la aplicación aplicando OWASP Top 10.

## Cuándo activar

- Código nuevo con manejo de autenticación, autorización o datos sensibles
- Previo a un release o merge a main
- Auditoría de seguridad solicitada sobre un módulo o servicio
- Fases: **Analizar, Diseñar, Construir, Verificar** (transversal)

## Cuándo NO invocar

- El cambio es un secret hardcodeado o credencial — usar `security-secrets-scan` (más rápido y específico).
- Se trata de CVEs en dependencias — usar `security-dependency-audit`.
- Se necesita cumplimiento formal contra estándar (PCI-DSS, ASVS) — usar `security-compliance`.


## OWASP Top 10 — Qué revisar

| ID | Categoría | Qué buscar en el código |
|---|---|---|
| A01 | Broken Access Control | Falta de verificación de permisos antes de operaciones sensibles |
| A02 | Cryptographic Failures | Datos sensibles sin cifrar, algoritmos débiles (MD5, SHA1), TLS deshabilitado |
| A03 | Injection | SQL/NoSQL/Command injection — inputs sin sanitizar concatenados en queries |
| A04 | Insecure Design | Ausencia de rate limiting, lógica de negocio sin validación de invariantes |
| A05 | Security Misconfiguration | Headers de seguridad ausentes, CORS permisivo (`*`), debug activo en producción |
| A06 | Vulnerable Components | *(ver `security-dependency-audit`)* |
| A07 | Auth Failures | Tokens sin expiración, passwords sin hash, sesiones sin invalidación |
| A08 | Integrity Failures | Deserialización de datos no confiables, verificación de firma ausente |
| A09 | Logging Failures | Eventos de seguridad sin loggear, datos sensibles en logs |
| A10 | SSRF | URLs construidas desde input del usuario sin validación de destino |

## Severidades

| Nivel | CVSS | Acción |
|---|---|---|
| **Critical** | 9.0–10.0 | Bloquea release — remediar antes de continuar |
| **High** | 7.0–8.9 | Remediar en el sprint actual |
| **Medium** | 4.0–6.9 | Ticket de seguimiento obligatorio |
| **Low** | 0.1–3.9 | Backlog de seguridad |

## Gotchas

- **Validar input solo en cliente** — la validación en JS es UX, no seguridad. Toda validación crítica debe replicarse en servidor. Asumir cliente comprometido.
- **Confiar en `Origin` o `Referer` para auth** — los headers son falsificables. Auth debe basarse en tokens firmados (JWT con verificación de firma), nunca en headers no autenticados.
- **String concat para queries con prepared statements parciales** — `db.query("SELECT * FROM users WHERE id = " + userId + " AND name = ?", [name])`. Mezclar concatenación con prepared anula la protección. Todos los inputs van como parámetros.
- **Stack trace en respuesta de error** — `500 Internal Server Error: Connection failed at /etc/db.conf:42`. Filtra estructura interna al atacante. En producción: log detallado server-side, mensaje genérico al cliente.
- **JWT sin verificación de algoritmo** — librerías que aceptan `alg: none` o `HS256` cuando se esperaba `RS256`. Pin explícito del algoritmo en la verificación.
