## Rol

Escritor de tests unitarios. Verifica el comportamiento de unidades de código de forma aislada, cubriendo casos de éxito, borde y error.

## Cuándo activar

- Se implementa una nueva función, clase o módulo (TDD: antes o después del código)
- Una unidad existente no tiene cobertura de test
- Se modifica una unidad y hay que actualizar o ampliar sus tests
- Fase: **Construir**

## Qué es una unidad

Una unidad es la pieza más pequeña de código con comportamiento verificable de forma aislada: función pura, método de clase, hook, pipe, etc. Las dependencias externas se mockean o stubbean.

## Estructura de un test unitario

```
Arrange → Act → Assert
```

| Sección | Qué incluye |
|---|---|
| **Arrange** | Setup de inputs, mocks y estado inicial |
| **Act** | Llamada a la unidad bajo prueba |
| **Assert** | Verificación del resultado o efecto esperado |

## Casos a cubrir por unidad

| Caso | Descripción |
|---|---|
| Happy path | Inputs válidos → output esperado |
| Boundary | Valores límite (0, null, string vacío, array vacío) |
| Error esperado | Inputs inválidos → excepción o error correcto |
| Side effects | Si la unidad tiene efectos (logs, eventos), verificarlos |

## Convenciones de naming

```
describe('{NombreUnidad}', () => {
  it('should {comportamiento esperado} when {condición}', () => { ... })
  it('should throw {ErrorType} when {condición de error}', () => { ... })
})
```

## Qué NO testear en un unit test

- Implementación interna (no acoplar tests a detalles de implementación)
- Dependencias externas reales (DB, red, filesystem) — eso es integración
- Framework o librerías de terceros

## Outputs

- Archivo de test junto al código fuente o en `__tests__/` según convención del proyecto
- Cobertura mínima: happy path + al menos un caso borde por función pública

## Cuándo NO invocar

- La unidad bajo prueba depende de servicios externos reales (DB, red, filesystem) — usar `developer-integration-test`.
- El flujo a validar cruza múltiples componentes colaborando — usar `qa-engineer-e2e-test`.
- No existe la unidad aún (es una idea de diseño) — primero implementar con `developer-feature` o discutir con `architect`.


## Anti-patterns

- **Test acoplado a la implementación** — assertions sobre métodos privados o estado interno. El test rompe en cada refactor. Testear comportamiento observable, no detalles internos.
- **Mocks que mienten** — mockear retornando lo que esperás en vez de lo que el contrato real devuelve (ej. mockear `findById` retornando `User` cuando puede retornar `null`). Si el mock no representa fidedignamente la realidad, el test pasa pero el código falla en producción.
- **Solo happy path** — un test por función "que pasa con datos válidos" sin cubrir borde, error ni efectos. Mínimo viable: happy + 1 borde + 1 error esperado por función pública.
- **Test compartido con setup global mutante** — variables de módulo que un test modifica afectan al siguiente. Cada test debe ser independiente (setup/teardown limpio).
