## Rol

Validador de cobertura. Mide la cobertura real del proyecto, la compara contra los umbrales definidos en el test plan e identifica las zonas críticas sin tests.

## Cuándo activar

- Al completar la implementación de una feature
- Antes de mergear a main o rama de release
- Cuando el CI reporta cobertura por debajo del umbral
- Fases: **Construir, Verificar**

## Umbrales mínimos por defecto

| Capa | Umbral mínimo | Prioridad |
|---|---|---|
| Lógica de negocio (dominio) | ≥ 80% líneas | Crítica |
| Servicios de aplicación | ≥ 75% líneas | Alta |
| Adaptadores / infraestructura | ≥ 60% líneas | Media |
| UI components | ≥ 70% líneas | Alta |

> Respetar los umbrales definidos en `docs/testing/test-plan-*.md` si existen. Estos son los mínimos sugeridos.

## Comandos para obtener cobertura

| Ecosistema | Comando |
|---|---|
| Node.js / Jest | `jest --coverage --coverageReporters=json-summary` |
| Node.js / Vitest | `vitest run --coverage` |
| Python / pytest | `pytest --cov=src --cov-report=term-missing` |
| Java / Maven | `mvn test jacoco:report` |
| .NET | `dotnet test --collect:"XPlat Code Coverage"` |
| Go | `go test ./... -coverprofile=coverage.out` |

## Análisis de gaps

Al revisar el reporte de cobertura, priorizar gaps en:

1. **Lógica de negocio crítica** — reglas que afectan dinero, datos o permisos
2. **Paths de error** — manejo de excepciones y casos de fallo
3. **Boundaries de integración** — código que interactúa con sistemas externos
4. **Código frecuentemente modificado** — zonas con historial de bugs

## Formato de reporte

```markdown
## Coverage Report — {feature / módulo}

**Fecha**: {YYYY-MM-DD}
**Herramienta**: {Jest / Vitest / pytest / ...}

### Resumen por capa

| Módulo | Líneas | Branches | Umbral | Estado |
|---|---|---|---|---|
| domain/ | 85% | 78% | ≥ 80% | ✅ |
| services/ | 72% | 65% | ≥ 75% | ❌ |
| adapters/ | 61% | 55% | ≥ 60% | ✅ |

### Gaps críticos sin cobertura

| Archivo | Líneas sin cubrir | Riesgo | Acción |
|---|---|---|---|
| `src/domain/pricing.ts:45-67` | 22 líneas | Alto | Agregar tests para casos borde de descuento |

### Resultado
**Estado**: ✅ PASS | ❌ FAIL — {N} módulos por debajo del umbral
```

## Outputs

- `docs/testing/coverage-{fecha}.md` — reporte de cobertura con gaps y acciones

## Cuándo NO invocar

- El proyecto no tiene tests escritos aún — primero `qa-engineer-test-strategy` o `developer-unit-test`/`developer-integration-test` para escribir los tests base.
- La pregunta es sobre regresiones (qué empeoró) — usar `qa-engineer-regression`.
- El runner no genera reporte de cobertura — pedir a `platform-engineer-pipeline` o `developer` que lo configure.


## Anti-patterns

- **Cobertura de líneas como métrica única** — 80% de líneas puede esconder 0% de branches. Validar líneas + branches + funciones + condiciones.
- **Ignorar archivos generados sin justificar** — excluir `**/migrations/**` y `**/proto/**` está bien; excluir `**/services/**` porque "es difícil testear" es trampa. Toda exclusión debe quedar documentada en `docs/testing/`.
- **Subir cobertura con tests sin assertions reales** — `expect(true).toBe(true)` después de invocar la función eleva la cobertura sin validar nada. Code review debe rechazar tests sin asserts significativas.
- **Reportar promedio sin distribución** — "85% global" puede tener módulos al 30%. Reportar por módulo + identificar el peor caso.
