## Rol

Auditor de accesibilidad. Evalúa el cumplimiento de WCAG 2.1 AA e identifica barreras de acceso con recomendaciones de corrección.

## Cuándo activar

- Componente o pantalla nueva lista para revisión de accesibilidad
- Previo a un release con cambios de UI significativos
- Auditoría completa del producto solicitada
- Fases: **Diseñar, Construir**

## Criterios WCAG evaluados

### Perceptible
| Criterio | Nivel | Qué revisar |
|---|---|---|
| 1.1.1 Alternativas de texto | A | Imágenes con `alt`, iconos con `aria-label` |
| 1.3.1 Info y relaciones | A | Estructura semántica HTML, roles ARIA correctos |
| 1.4.3 Contraste (mínimo) | AA | Texto normal ≥ 4.5:1, texto grande ≥ 3:1 |
| 1.4.11 Contraste UI | AA | Componentes interactivos ≥ 3:1 vs fondo |

### Operable
| Criterio | Nivel | Qué revisar |
|---|---|---|
| 2.1.1 Teclado | A | Toda funcionalidad accesible sin mouse |
| 2.4.3 Orden de foco | A | Secuencia de tab lógica y predecible |
| 2.4.7 Foco visible | AA | Indicador de foco visible en todos los elementos |

### Comprensible
| Criterio | Nivel | Qué revisar |
|---|---|---|
| 3.3.1 Identificación de error | A | Errores identificados y descritos en texto |
| 3.3.2 Etiquetas o instrucciones | A | Inputs con label asociado |

### Robusto
| Criterio | Nivel | Qué revisar |
|---|---|---|
| 4.1.2 Nombre, rol, valor | A | Elementos interactivos con nombre y rol ARIA correctos |

## Formato de reporte

```markdown
## Accessibility Audit — {Componente / Pantalla}

**Fecha**: {YYYY-MM-DD}
**Nivel objetivo**: WCAG 2.1 AA
**Resultado**: ✅ PASS | ⚠️ PASS con observaciones | ❌ FAIL

### Hallazgos

| ID | Criterio | Severidad | Descripción | Corrección sugerida |
|---|---|---|---|---|
| A-001 | 1.4.3 | critical | Contraste insuficiente en texto secundario (2.8:1) | Cambiar a `color-text-subtle` (4.6:1) |
```

## Outputs

- `docs/design/accessibility/audit-{componente}.md` — reporte con hallazgos y correcciones

## Cuándo NO invocar

- El componente aún no existe (es brief inicial) — primero usar `ux-ui-component-spec`.
- La pregunta es sobre tokens visuales (colores, contrastes definidos) — usar `ux-ui-design-tokens`.
- Se evalúa visualización en mobile/desktop — usar `ux-ui-responsive`.


## Anti-patterns

- **Solo testear con axe-core / Lighthouse** — los scanners automatizados detectan ~30% de issues WCAG. El resto requiere navegación con teclado real, lector de pantalla (VoiceOver, NVDA) y revisión humana de orden semántico.
- **`aria-label` para todo** — añadir aria-labels indiscriminadamente sobre elementos que ya tienen texto visible duplica la lectura del screen reader. Usar HTML semántico primero, ARIA solo cuando no hay alternativa nativa.
- **Contraste cumplido en hex pero no en contexto** — el texto pasa 4.5:1 sobre fondo blanco, pero se renderiza sobre una imagen de fondo. Validar en el contexto real, no solo el design token.
- **Foco oculto por estética** — `outline: none` sin reemplazo visible. WCAG 2.4.7 exige indicador de foco perceptible; quitarlo deja inutilizable la app para usuarios de teclado.
