# Guía de migración — 2.25.x → 2.26.0

Esta guía describe qué cambia para un proyecto que adopta el template ASDD al
pasar de la serie 2.25.x a la versión 2.26.0. El cambio central es el **modelo
de especificación spec-per-área** (ADR-004). Es un cambio MINOR: aditivo y
backward-compatible con los artefactos existentes.

Referencia canónica: ADR-004 «spec-per-area model», en el repositorio del template ASDD.

## Resumen del cambio

| Antes (≤ 2.25.4) | Ahora (2.26.0) |
|---|---|
| La fase Analizar producía una **spec monolítica** por funcionalidad (`{feature}-NNN.md`) con vocabulario `CU-`/`HU-`/`AC-`. | La fase Analizar produce un **set spec-per-área**: 1 INDEX + 1 spec-funcional + N `spec-{area}`. |
| Partición de specs por **tamaño** (umbrales 300 líneas / ≤5 CU / ≤1 aggregate), enforzada por `spec-size-guard`. | Partición **estructural por área** de dominio (WF-002-STRUCT). Sin límite de tamaño por archivo. |
| Un solo autor (`producto`) escribía toda la spec. | Autoría multi-dominio en paralelo — cada dominio con `Aplica = Sí` autora su slice. |
| Construir leía la spec completa. | Construir se ejecuta como loop determinista dirigido por el INDEX (`index_ref`), con grafo de olas por dependencias. |

## 1. Nuevo modelo de specs: cómo se generan ahora

Al ejecutar `/sofka-asdd:analyze`, el flujo produce tres tipos de artefactos bajo
`docs/specs/`:

1. **spec-funcional** (`{run_id}-ANALYZE-{SEQ}-{feature}-funcional.md`) — SSoT del
   contenido cross-área. Lo autora `sofka-asdd-producto` (skill `funcional`) con el
   orden de sub-roles `ba → funcional → po`. Contiene el **Mapa de dominios (§0)**
   que marca qué áreas aplican.
2. **N `spec-{area}`** (`{run_id}-ANALYZE-{SEQ}-{feature}-{area}.md`) — un slice
   canónico por cada área con `Aplica = Sí` en el Mapa. Áreas posibles:
   `backend`, `frontend`, `diseno`, `devops`, `seguridad`, `data`, `qa`
   (7 áreas — el slug `-diseno` usa ASCII, sin ñ ni tilde).
   Cada dominio autora su propio slice en paralelo.
3. **INDEX** (`{run_id}-ANALYZE-{SEQ}-{feature}-index.md`) — orquesta el progreso
   por área y declara el grafo de dependencias. Es la SSoT del estado de cada área.

El cierre de Analizar exige el **Gate DOR** (WF-002-DOR): dominio Funcional
`APROBADA`, cada área `Aplica = Sí` en `COMPLETO`, y opt-out de Seguridad con
sign-off explícito de `sofka-asdd-security`.

### Vocabulario nuevo (ADR-004 §6)

Se retiran `CU-\d+`, `HU-\d+` y `AC-\d+`. El super-spec usa:

- **Reglas de Negocio `RN-\d+`** tipadas `[CORE]` / `[EDGE]`.
- **Flujo de Negocio** numerado sin ID.
- Una **User Story** libre única.
- Escenarios **Gherkin** sin ID (con IDs sintéticos `SCN-NNN` derivados del orden
  de aparición para trazabilidad).
- Gaps → `GAP-\d+`; cambios post-aprobación → `CR-\d+`.

## 2. Construir dirigido por el INDEX

`/sofka-asdd:build` ahora se ejecuta como loop determinista dirigido por el INDEX
del feature (`.asdd-run.json.phases.build.index_ref`). El orquestador recorre las
áreas según el grafo de olas:

- **Ola 1** (sin dependencias entrantes, arrancan en paralelo): `seguridad`,
  `diseno`, `backend`, `data`.
- **Ola 2**: `frontend` (depende de `diseno` + `backend`), `devops` (depende de
  `backend`).
- **Ola 3**: `qa` (depende de `backend` + `frontend`).

Solo el orquestador escribe el INDEX (R-INDEX-5): marca cada área `done` con
timestamp y commit SHA. Los developers reportan estado vía payload de retorno,
nunca escriben el INDEX. El área `diseno` no usa worktree (produce artefactos de
diseño, no código).

## 3. Guard retirado: `spec-size-guard`

El hook `sofka-asdd-pre-tool-use-spec-size-guard.mjs` se **retira** (WU-1). Ya no
existe un límite cuantitativo de tamaño por spec. La partición ahora es
**estructural por área** (WF-002-STRUCT): una spec por área con `Aplica = Sí`,
sin importar cuántas líneas ocupe.

Acción para el proyecto consumidor: si tu `.claude/settings.json` referencia
explícitamente `spec-size-guard` en la cadena `PreToolUse`, remové esa entrada al
adoptar 2.26.0. Los demás guards de la cadena (`analyze-guard`,
`artifact-name-guard`) se mantienen sin cambios.

## 4. Backward-compatibility del naming legacy

Los artefactos con el naming anterior (`{feature}-NNN.md`, vocabulario `CU-`/`HU-`)
siguen siendo reconocidos por la cadena de guards y no se rompen. La migración es
**forward-only**: los features nuevos se analizan con el modelo spec-per-área; los
specs existentes no requieren reescritura para seguir compilando ni pasando los
gates.

El `artifact-name-guard` valida únicamente operaciones `Write` (creación de
artefactos), no `Edit`. Por eso las ediciones de artefactos vivos (INDEX,
`spec-{area}`) durante Construir no requieren exención especial.

## Checklist de adopción

- [ ] Bump del template a 2.26.0 (verificar `lock.version` ↔ `ASDD-CHANGELOG.md`).
- [ ] Remover `spec-size-guard` de la cadena `PreToolUse` si estaba referenciado.
- [ ] Familiarizarse con el nuevo Mapa de dominios (§0) del spec-funcional-template.
- [ ] No es necesario migrar specs existentes — el naming legacy sigue soportado.
