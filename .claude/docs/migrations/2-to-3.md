# Migración ASDD — 2.x → 3.0.0

Esta guía cubre la actualización de un proyecto consumidor ASDD 2.x al runtime
3.0.0. Es una migración **MAJOR**: cambia rutas y registros internos del runtime,
la autorización de agentes y la convención para artefactos nuevos.

## Resumen de incompatibilidades

| En 2.x | En 3.0.0 | Acción requerida |
|---|---|---|
| Varios hooks `PreToolUse` registrados por matcher | Un dispatcher para `Bash|Write|Edit` | Reemplazar la cadena por `asdd-pre-tool-dispatcher.mjs`. |
| Cinco hooks ASDD en `SessionStart` | Un dispatcher de sesión | Registrar `asdd-session-start-dispatcher.mjs` y retirar `asdd-session-start.mjs`. |
| Rules especializadas siempre activas en `.claude/rules/` | Núcleo compacto + referencias bajo demanda | Distribuir `.claude/references/` y usar `asdd-resolve-rule.mjs`. |
| Skills especializadas precargadas en agentes | Capability primaria y dependencias explícitas | Distribuir catálogos/loaders y no restaurar `skills:` eager retiradas. |
| Aprobación de plan enfocada en el launch | Binding de launch y cada operación | Incluir scope, comandos, capability, modelo y marcador `ASDD-BUDGET` exactos. |
| Commit podía confundirse con el lote de implementación | Challenge de commit independiente | Autorizar `git commit` con `asdd-commit-authorization.mjs`. |
| Nombres de documentos dependientes del agente | `{run_id}-{PHASE}-{SEQ}-{slug}.{ext}` | Ejecutar bootstrap antes del plan y usar la ruta reservada. |
| Opus global por defecto | Sonnet + routing `TRIVIAL|LIGHT|MEDIUM|FULL` | No fijar Opus para compensar contexto; dejar escalar riesgo/complejidad. |
| Worktree forzado en developers | Worktree opt-in | Declarar aislamiento únicamente cuando el proyecto lo necesite. |

## Antes de migrar

1. Confirmar que el proyecto consumidor está limpio:

   ```bash
   git status --short
   ```

2. Crear una rama de actualización propia. No mover ni reutilizar el tag
   `v2.27.4`.
3. Respaldar personalizaciones del consumidor en `CLAUDE.md`,
   `.claude/settings.json`, agents y hooks. Estos archivos se fusionan; no se
   deben reemplazar silenciosamente con disclaimers o datos exclusivos del
   template.
4. Conservar `.asdd-run.json`, `docs/runs/**` y artefactos del proyecto. No
   copiar el estado de ejecución del repositorio template.

## Pasos de actualización

### 1. Instalar la distribución 3.0.0

Usar la actualización del CLI compatible con contrato `2.3.x`, o copiar la
distribución declarada en `.asdd/cli-contract.json`. Son obligatorios:

- `.claude/ba-steps/` y `.claude/atf-web-steps/`;
- `.claude/references/` y el núcleo compacto de `.claude/rules/`;
- `.claude/scripts/lib/`;
- loaders/resolvers de rules y capabilities;
- autorización de plan y commit;
- routing, bootstrap, naming y reconciliación de runs;
- dispatchers `PreToolUse` y `SessionStart`.

Una copia parcial no es compatible con 3.0.0 y debe fallar en
`cli-runtime-distribution`.

### 2. Reemplazar registros de hooks

Tomar como referencia `.claude/settings.json` de 3.0.0:

- `PreToolUse` con matcher `Bash|Write|Edit` ejecuta únicamente
  `asdd-pre-tool-dispatcher.mjs` para la cadena ASDD;
- `SessionStart` ejecuta `asdd-session-start-dispatcher.mjs`;
- hooks externos como collectors mantienen procesos separados;
- eliminar referencias a hooks ASDD trasladados a
  `.claude/scripts/legacy-hooks/`.

No registrar simultáneamente dispatcher y cadena legacy: duplicaría decisiones
y latencia.

### 3. Adoptar carga bajo demanda

Distribuir los manifiestos:

```text
.asdd/rule-loading.json
.asdd/capability-loading.json
.asdd/coordinator-loading.json
```

Antes de invocar un agente con capability, el prompt debe contener y el agente
debe ejecutar:

```bash
node .claude/scripts/asdd-load-capability.mjs <capability>
```

La ruta absoluta solo es equivalente cuando apunta al mismo loader dentro del
proyecto.

### 4. Adoptar autorización operacional

Los planes MEDIUM/FULL declaran agente, scope, comandos, capability, modelo,
turnos y retries. El prompt del Agent contiene el marcador `ASDD-BUDGET` exacto.
Una diferencia requiere un challenge nuevo; nunca se amplía mediante un permiso
nativo.

Los cambios `LIGHT atomic_scoped_change` pueden usar autorización interna de un
archivo y un uso sin challenge visible. Si el scope no se resuelve de manera
unívoca, el runtime falla cerrado y vuelve al gate normal.

### 5. Inicializar runs y nombres nuevos

Antes del primer plan de Specify:

```bash
node .claude/scripts/asdd-run-bootstrap.mjs \
  --feature <feature> \
  --phase specify \
  --artifact-dir docs/specs \
  --artifact-slug brief-<feature>
```

Usar el `artifact_path` retornado en el plan, scope y prompt del agente. Los
documentos legacy no se renombran; la convención universal aplica a creaciones
nuevas bajo `docs/**`.

## Validación posterior

Ejecutar desde la raíz del consumidor:

```bash
node .claude/scripts/validate-template.mjs
node .claude/scripts/asdd-route-request.mjs \
  --file docs/contexto/prompts/00-auditoria-contexto.md
```

> **Las suites `test-*.mjs` NO se distribuyen y no van a distribuirse.** Son tooling del equipo
> mantenedor: verifican el comportamiento interno de hooks y scripts del framework, no la configuración
> de tu proyecto. Lo que sí valida tu instalación es `validate-template.mjs`, que ya recibís y que corre
> automáticamente en el `post_install` del CLI. Si el validador da `0 errores`, tu migración está bien.

Resultado de referencia de 3.0.0:

- validator: `32 OK`, `0 errores`;
- LIGHT atómico: scope exacto, un uso y rechazo fuera de scope;
- bootstrap: idempotencia, ruta reservada y naming universal.

Los warnings de presupuesto de contexto documentados en el CHANGELOG no bloquean
la adopción, pero no deben ocultarse como PASS.

## Rollback

Si la actualización bloquea un flujo crítico:

1. restaurar los archivos versionados desde la rama previa del consumidor;
2. volver a la distribución del tag `v2.27.4` sin mover ese tag;
3. restaurar el registro legacy de hooks correspondiente a esa versión;
4. conservar los artefactos de negocio y run creados: no requieren borrado;
5. documentar el mismatch antes de reintentar la migración.

No mezclar archivos runtime 2.x y 3.x: dispatchers, manifiestos y librerías de
autorización forman una unidad de distribución.
